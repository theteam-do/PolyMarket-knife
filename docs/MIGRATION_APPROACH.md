# 迁移方案调整建议

**日期**: 2026-03-01  
**状态**: 🟡 需要决策

---

## 📊 当前情况

### 官方 SDK 复杂度

官方 `polymarket-client-sdk` (v0.4.3) 的 API 设计非常复杂：

1. **类型状态机**: `Client<Unauthenticated>` / `Client<Authenticated<Normal>>`
2. **Builder 模式**: 所有请求都需要使用 builder
3. **签名分离**: 订单需要先用 `sign()` 签名，再用 `post_order()` 提交
4. **非直观 API**: 
   - `order_book()` 而不是 `get_orderbook()`
   - `midpoint()` 而不是 `get_midpoint()`
   - `cancel_order(uuid)` 需要 UUID 类型

### 适配层困难

创建适配层遇到的主要问题：

1. **类型暴露**: 需要暴露官方 SDK 的泛型状态
2. **API 映射**: 官方 API 与我们的预期完全不同
3. **依赖复杂**: 需要正确导入所有类型和 trait

---

## 💡 建议方案

### 方案 A：直接在策略中使用官方 SDK（推荐）

**理由**：
1. 适配层复杂度接近重写整个客户端
2. 官方 SDK 文档完善，示例丰富
3. 可以直接利用官方 SDK 的所有功能
4. 长期维护成本更低

**实施步骤**：
1. 删除 `poly-adapter` 适配层
2. 直接在每个策略中引用官方 SDK
3. 基于官方示例重写策略的 API 调用部分
4. 保留策略逻辑和风控模块

**工作量**：约 3-5 天

---

### 方案 B：继续完善适配层

**理由**：
1. 保持策略代码不变
2. 统一的 API 抽象

**问题**：
1. 需要深入理解官方 SDK 的所有细节
2. 适配层复杂度接近官方 SDK 本身
3. 长期维护两份代码

**工作量**：约 5-7 天

---

### 方案 C：混合方案

**核心策略**使用官方 SDK 直接调用，**简单策略**使用简化的适配层。

---

## 🎯 我的建议

**推荐方案 A**，原因：

1. **时间效率**: 3-5 天 vs 5-7 天
2. **代码质量**: 直接使用官方 API，减少中间层错误
3. **维护成本**: 只需维护策略逻辑，不需要维护适配层
4. **学习价值**: 团队直接掌握官方 SDK 使用
